# ADR-023: Hub CLI Default Command and Root Help Routing

> **Amends [ADR-020](ADR-020-hub-cli-command-surface.md)**: the CLI framework choice,
> blocking execution model, exit codes, and containment rule C9 from ADR-020 remain
> unchanged. This ADR only replaces the root dispatch gate and the root help rendering
> shape.

## Context and Problem Statement

ADR-020 established the Hub CLI as a Spectre.Console.Cli command surface and documented
the in-process blocking execution model. It originally routed `Program.cs` through a
manual `ShouldDispatchToCli` gate and described a hand-padded root help section for the
server switches.

That shape is too fragile for the help contract and too indirect for the startup path.
Spectre already knows how to render command options for the active command, so the root
invocation should be treated as a real default command instead of a special-case branch.
That keeps `-h/--help` aligned with the actual command model and removes the need for a
custom "Server options:" block.

This is a cross-cutting CLI routing change, so per constitution it belongs in a new ADR
that amends the existing command-surface decision instead of rewriting ADR-020 in place.

## Decision Drivers

- The root help output must be generated by Spectre, not assembled by string-patching.
- `PathSwitchCatalog.All` must remain the single source of truth for path switches.
- The web-host startup path must stay available without a separate pre-parser branch.
- `--help` / `-h` precedence and the existing command surface must remain unchanged.

## Considered Options

- **Keep the manual `Program.cs` gate and custom help block**. Rejected: it duplicates
  the command model, keeps root help out of Spectre's generated options grid, and leaves
  the startup path split across two code paths.
- **Use `System.CommandLine` for the root routing/help layer**. Rejected: it would work
  for parsing, but ADR-020 already standardized on Spectre.Console.Cli for the command
  surface, so introducing a second CLI framework would add a parallel abstraction without
  solving the help-routing issue better than the default-command approach.
- **Use `Terminal.Gui` for a richer TUI startup/help experience**. Rejected: this change
  is about command routing and generated help, not building an interactive terminal UI.
  Terminal.Gui would introduce a separate UI stack and pull the feature away from the
  scriptable CLI contract.
- **Use a Spectre default command**. Chosen: it keeps one parser, one command model, and
  lets Spectre render the root `OPTIONS:` section directly from `HubPathSettings`.

## Decision

1. `HubRootCommand` is the Spectre **default command** for the Hub CLI. When no command
   name is supplied, the command app starts the web host through the same in-process
   composition path used by the other commands.
2. `Program.cs` becomes a single pass-through:
   `return await HubCliApp.RunAsync(args);`
3. Root help uses Spectre's generated `OPTIONS:` section for `HubPathSettings`, so the
   path switches appear in the standard options grid instead of a hand-padded
   "Server options:" block.
4. `PathSwitchCatalog.All` still owns the switch list and parity tests still guard the
   1:1 mapping.
5. All blocking execution, exit codes, telemetry flush behavior, and containment rules
   from ADR-020 remain unchanged.

## Consequences

- The CLI startup model is simpler: one parser, one command model, one pass-through
  entry point.
- Help rendering now reflects Spectre's real command model directly.
- The dispatch behavior documented in ADR-020 is superseded without rewriting the rest of
  that ADR.

## Structural Enforcement

| Rule | Test |
| --- | --- |
| Default-command startup path is used for root invocation | `HubRootCommand` / `HubCliApp` integration test |
| Root help renders generated `OPTIONS:` output for `HubPathSettings` | `HubHelpUsageTests` |
| `PathSwitchCatalog.All` remains the single declaration point | existing parity test |
