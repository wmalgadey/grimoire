# Research: Task Visibility & Recovery Improvements

**Feature**: `023-task-ui-improvements` | **Date**: 2026-08-13

All Technical Context unknowns are resolved below. Sources: full read of all 24 ADRs + `docs/adr/index.md`, and code inspection of the Hub ingest path, operational store, lifecycle publisher, run coordinator, board projection, and frontend board/detail views.

## R1 — Where the status history lives

**Decision**: A new append-only table `ingest_status_history` in the existing Hub-owned SQLite operational-state database (`OperationalStateRepository`), written at the Hub's lifecycle-transition choke point. One row per transition: `task_id`, `status`, `entered_at`, optional `detail` (e.g., failure reason, attempt number), monotonic `seq` per task.

**Rationale**: ADR-003 assigns Hub operational bookkeeping to the SQLite store and markdown to domain state. The task artifact (`<MemoryDir>/tasks/{taskId}.md`) has multiple writers already — the Hub pipeline writes `received`/`converting`/`queued` and the agent process writes `running`/`completed`/`failed` — so appending history to the artifact would create write contention across processes (exactly what ADR-015's guard exists to arbitrate for wiki files) and would put Hub-owned diagnostics in an agent-owned file (against ADR-002's ownership split and ADR-024's re-anchoring of harness records). The existing `operational_task_state` rows are transient (deleted in `FinishRunAsync`), so history must be its own durable, append-only table. The Hub observes every transition (its own pipeline stage writes plus agent NDJSON events surfaced through `IngestLifecyclePublisher`), making the publisher the single reliable recording point.

**Alternatives considered**: (a) Frontmatter list in the task artifact — rejected: multi-process write contention, agent-owned file, and the artifact is rewritten wholesale by the agent's writer (unknown fields at risk). (b) Separate markdown history file per task — rejected: operational data in a domain-state medium contradicts ADR-003; nothing needs it to be git-friendly. (c) Deriving history from OTel logs — rejected: telemetry is an observer, not a system of record; not queryable by the detail endpoint.

## R2 — Reactivation mechanics and backoff scheduling

**Decision**: On liveness-window expiry, `IngestRunCoordinator` records a `liveness_interrupted` history entry, terminates the silent process, and — if attempts remain — schedules a re-launch of the same task id via the existing `IAgentProcessLauncher` port after an increasing delay (default schedule: 10 s, 30 s, 90 s; max 3 attempts, code-level constants alongside the existing `livenessWindow` constructor default). Scheduling uses the .NET `TimeProvider` abstraction injected into the coordinator so deterministic tests drive time with a concrete `FakeTimeProvider`. After the final attempt fails, `FinishRunAsync(taskId, "failed", …)` runs exactly as today (Hub failure artifact, queue advance, `ingest.run.liveness_failed`). While a reactivation is pending, the run slot remains held so the FIFO single-slot model (ADR-008) is undisturbed; the operational-state row gains an `attempt` counter.

**Rationale**: ADR-008's liveness rule stays the detection authority — only the consequence changes from "immediately terminal" to "bounded re-entry", which is precisely the amendment ADR-025 records (revoking ADR-002's explicit retry deferral). Holding the slot during backoff avoids interleaving a reactivating task with the next queued task and keeps `TryStartNextAsync` untouched. `TimeProvider` satisfies ADR-021's deterministic-wait ban (no `Task.Delay` against a wall clock in tests) without introducing a mocking framework — `FakeTimeProvider` is a concrete fake for a BCL abstraction, consistent with Principle II's classicist rules.

**Alternatives considered**: (a) Release the slot and re-enqueue at queue tail per attempt — rejected: reorders work the operator scheduled, complicates queue semantics, and makes "attempt" state span queue entries. (b) Unbounded retry — rejected in clarification (2026-08-13). (c) Fixed-interval retry — rejected in clarification; increasing backoff chosen. (d) Configurable attempts/backoff in `appsettings.json` — deferred: ADR-022's configuration surface is deliberately minimal and path-scoped; the spec records these as operational tuning values, so constructor-default constants (the existing `livenessWindow` pattern) suffice until an operator need appears.

## R3 — Manual restart of a finally-failed task

**Decision**: New coordinator method `RestartFailedAsync(taskId)` exposed as `POST /api/ingest-submissions/{taskId}/restart`. Preconditions verified from current state: task's artifact status is `failed` AND the task is not queued/running (no operational row). Acceptance performs, atomically under the coordinator lock with a compare-and-swap style guard on persisted state: append `restarted` + `queued` history entries, reset the attempt counter, write the `queued` stage to the task artifact via the Hub writer, insert the task at the queue tail, publish the lifecycle event, then `TryStartNextAsync`. Duplicate or invalid requests get a conflict result (HTTP 409), mirroring the existing `RetriggerAsync` false→409 pattern. The normalized markdown for the task (`<DataDir>/raw/sources/{taskId}.md`) must still exist; if missing, restart is rejected with a clear reason. No new CLI command: the spec's requirement is UI access; `ingest-retrigger` keeps its existing, distinct meaning (re-arming a paused queue) and ADR-020's parity principle is preserved because the endpoint is a thin wrapper over the shared coordinator method that a future CLI command could also call.

**Rationale**: Re-using the same task id and appending to its history is what the spec's clarifications fixed ("re-uses the existing task record and identifier"). The CAS-under-lock idiom is the repo's established deterministic race arbiter (ADR-018's withdrawal race). Verifying the normalized source still exists prevents relaunching an agent against nothing (edge case in spec).

**Alternatives considered**: (a) Creating a new task cloned from the failed one — rejected: contradicts spec assumption, splits history across ids. (b) Overloading `RetriggerAsync` — rejected: it operates on queued tasks with the queue paused; conflating the two verbs invites exactly the state-model confusion the spec is trying to remove. (c) Adding an `ingest-restart` CLI command now — deferred as out of spec scope; noted in ADR-025 as a recognized future single-file amendment to ADR-020's command table.

## R4 — Human-readable task label (title)

**Decision**: Title extraction happens once, deterministically, in `IngestSubmissionPipeline` at normalization time: first ATX `# ` heading of the normalized markdown (trimmed, capped at 120 chars); fallback chain = original uploaded filename (for file submissions — persisted from `file.FileName`, which today is discarded after extension sniffing) → submitted URL (for URL submissions) → task id. The title and original filename are stored as new fields in the source-artifact manifest sidecar (`{taskId}.manifest.json`), which is Hub-owned and never touched by the agent. `KanbanBoardProjectionStore` and the detail endpoint read the manifest to populate `title`, replacing the current `Path.GetFileName(sourceRef)` value (which is effectively the task id). Tasks predating the feature (no title in manifest) fall back at read time to the same chain.

**Rationale**: The manifest is the only per-task metadata store with a single writer (the Hub pipeline), so no write contention and no agent-artifact coupling. First-H1 extraction is a deterministic string operation on already-produced conversion output — display metadata, not wiki-content judgment, so Principle V is untouched (the clarification session fixed "content-extracted title" and the spec's assumption limits it to reusing existing pipeline output). Read-time fallback covers pre-existing tasks without migration.

**Alternatives considered**: (a) Frontmatter `title:` in the task artifact — rejected: shared-write contention (see R1). (b) Asking the ingest agent to produce a title — rejected: adds an LLM dependency to a display label, makes board rendering depend on agent completion, and the spec explicitly assumes no new content-analysis capability. (c) HTML `<title>` extraction for URL sources — folded in implicitly: MarkItDown conversion already renders the page title as the leading heading when present; the first-H1 rule picks it up without a second extraction path.

## R5 — Source link and serving local files

**Decision**: The task detail response gains a `source` object: `{ kind: "url" | "file", href, available }`. For URL submissions, `href` is the submitted URL itself (direct anchor, `target="_blank"`). For file submissions, `href` is a new read-only Hub endpoint `GET /api/ingest-submissions/{taskId}/source/original` that streams the persisted original from `<DataDir>/raw/originals/{taskId}{ext}` with the `Content-Type` recorded in the manifest (`OriginalContentType`), `Content-Disposition: inline`. The path is composed exclusively from the validated task id via `ResolvedGrimorePaths`/`RawStoragePaths` — the endpoint never accepts a path parameter, so no traversal surface exists. If the original file or manifest is missing, the endpoint returns 404 and the detail response carries `available: false`, which the UI renders as a non-link "source unavailable" indicator.

**Rationale**: Serving only the already-persisted raw copy keeps this inside ADR-001's existing HTTP surface and ADR-010's persistence exemption — no new external system, no new ADR needed (confirmed against the ADR corpus; serving arbitrary operator-disk paths WOULD have been a new read surface and was rejected for that reason). Deriving the link server-side (rather than letting the frontend guess from `sourceRef`) keeps the URL-vs-file split and availability check in one tested place.

**Alternatives considered**: (a) `file://` links — rejected in clarification (breaks when browser and Hub are on different machines; browsers block them). (b) Serving the normalized markdown instead of the original — rejected: the spec asks for the *original* source; normalized view already exists via the task record. (c) A generic static-file mount over `RawDir` — rejected: broader exposure than needed, bypasses per-task availability logic.

## R6 — Board card decluttering and frontend integration

**Decision**: `TaskCard.svelte` drops its `StatusBadge` and renders the title as the primary label with the task id as muted secondary text; `KanbanColumn` headers are unchanged (they already name the stage). The detail page heading becomes the title with the task id shown beneath it (still copyable; unchanged URL scheme). A new `StatusHistoryPath.svelte` renders the ordered history (status, timestamp, detail) with the current entry highlighted; interruption/reactivation entries render inline in the list — the board's column model is untouched (clarification 2026-08-13: history-list only, no new columns). Restart is a button on the detail page shown only when status is `failed`; it calls the restart endpoint, disables while in flight, and surfaces 409 by refreshing to the task's true current state. Board and detail keep receiving live updates via the existing SignalR events; the detail page re-fetches history on `taskLifecycleChanged` for its task (no new SignalR event type needed).

**Rationale**: Minimal surface change consistent with the existing SignalR-push architecture (ADR-001); reusing `taskLifecycleChanged` as the history-refresh trigger avoids a new event contract while keeping the history authoritative from the endpoint.

**Alternatives considered**: (a) New `statusHistoryChanged` SignalR event carrying rows — deferred: redundant with a re-fetch on the existing event; can be added later if chattiness becomes an issue. (b) Optimistic local history append in the frontend — rejected: two sources of truth for an audit trail.

## R7 — Test approach for time- and race-dependent behavior

**Decision**: All reactivation/backoff tests run in `Grimoire.IntegrationTests` against the real coordinator + real SQLite file + `FakeAgentProcessLauncher` (existing hand-rolled port fake, extended with a "go silent" mode if not already present) + `FakeTimeProvider` advancing virtual time; assertions are state-based on history rows, queue state, and published lifecycle events. Restart race tests issue concurrent restart calls against the real coordinator and assert exactly one `restarted` history entry and one queue insertion. Frontend behavior (badge removal, title rendering, history path, restart button states, unavailable-source indicator) is covered by vitest browser-mode component tests colocated with the components. Observability contract tests follow the `HubRequestTracingTests` production-wiring pattern (`AddHubTelemetry` + in-memory exporters on TestServer) for every new metric, log event, and span, including request-span parentage for the two new endpoints.

**Rationale**: Direct application of Principle II (classicist, real infrastructure), ADR-021 (no wall-clock waits in deterministic tests), and Principle IV's production-wiring mandate written from the Feature-003 sampler incident.

**Alternatives considered**: Unit-testing a backoff calculator in isolation — unnecessary: the schedule is three constants; the behavior worth protecting is the coordinator's observable lifecycle, which the integration tests assert.
